# v0.23.2 + v0.23.3 — XSF multi-DATAGRID + CHGCAR spin/SOC — completion log

**Status**: ✅ both complete. **Date**: 2026-07-22.

## 23.2 — XSF multi-DATAGRID

`src/parsers/xsfParser.ts`:
- `parseDatagrid3D` (single) → `parseDatagrids3D` (returns `VolumetricData[]`):
  loops over every `BEGIN_DATAGRID_3D` across all BLOCK sections; each grid
  named from its `BEGIN_DATAGRID_3D_<label>` suffix (fallback `datagrid_N`);
  per-grid `trimRedundantPeriodicPlanes`; caller applies `snapGridLatticeToCell`.
- New `parseDatagrids3DFromBytes` (byte/streaming): finalizes each grid at
  `END_DATAGRID_3D`, resumes scan for the next `BEGIN`; stride per grid;
  trim only when `stride === 1`.
- `parseXsf` / `parseXsfTraj` / `parseXsfFromBytes` now return `volumetrics[]`
  (+ `volumetric` = `[0]` alias). `index.ts` XSF branches destructure both.

**Deviation**: manual says multi-block XSF with differing cell vectors should
error. We *tolerate* it — each grid renders independently, which is the useful
behavior; mismatched framing surfaces visually, not as a hard failure.

## 23.3 — CHGCAR spin/SOC

`src/parsers/chgcarParser.ts`:
- `parseChgcar` + `parseChgcarFromBytes` read **all** grid blocks. Blocks are
  separated by PAW `augmentation occupancies` sections; the next density block
  starts at a repeated `nx ny nz` dims line (`isDimsLine` detector).
- `buildChgcarGrids()` classifies by block count:
  - 1 → `[charge]` (non-spin)
  - 2 → `[charge, magnetization, spin_up, spin_down]` with
    `spin_up=(c+m)/2`, `spin_down=(c−m)/2`
  - 4 → `[charge, magnetization_x, magnetization_y, magnetization_z]`
  - Every grid volume-normalized (`1/cellVolume`, existing convention);
    magnetization/σ tagged `kind:'signed'`, charge/spin `kind:'scalar'`.

**Deviation from plan D3**: spin_up/down derived **eagerly** at parse time
(4 grids resident) rather than lazily on selection. Rationale: lazy needs a
derived-grid spec in the selection layer (23.4), making 23.3 non-self-
contained; eager matches the manual's 4-entry Model Tree and is directly
testable now. Memory (≤4× a single grid for collinear) is bounded by the
v0.22 `matviz.volumetric.maxGridPoints` decimation applied during ingestion.
If a real workflow hits memory pressure, revisit lazy derivation as a
follow-up (does not change the data model or UI).
