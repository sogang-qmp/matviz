# v0.20.1 feat 1 — Volumetric zero-copy postMessage

Shipped 2026-05-19. Single-feature patch release. Tier 1 of the
v0.22 large-volumetric plan (`plans/v0.22_large-volumetric.md`),
pulled out as a standalone patch because the change is universal
(benefits every cube/XSF/CHGCAR load, not just exciton-wavefunction-
scale files) and the edit surface is three lines.

## Problem

Loading any volumetric file (Gaussian Cube, XSF
`BEGIN_DATAGRID_3D`, VASP CHGCAR) into the webview held the grid in
memory three times simultaneously:

1. Parser allocates `Float32Array(N)` — 4N bytes.
2. `crystalEditorProvider.ts` calls `Array.from(c.volumetric.data)`
   to serialize for postMessage, producing a boxed `number[]` —
   8N bytes.
3. Structured-clone across the host → webview process boundary
   duplicates that `number[]` — another 8N bytes (webview side).
4. `renderer.loadVolumetric()` calls
   `new Float32Array(data.data)` to re-pack it — 4N bytes.

Total ≈ 24N bytes simultaneously in memory for an N-point grid.

Root cause was a defensive-typing mistake: the message-channel type
in `src/webview/message.ts` declared `data.data: number[]`, which
forced `Array.from` boxing on the send side and a wrap on the
receive side, neither of which is necessary because VSCode's
webview `postMessage` has supported efficient `ArrayBuffer` /
TypedArray transfer since `engines.vscode >= 1.57`
(`@types/vscode/index.d.ts:10000-10028`), and our `engines.vscode`
is `^1.85.0`.

## Change

Three edits:

- `src/webview/message.ts:9` — `data: number[]` → `data: Float32Array`.
- `src/editor/crystalEditorProvider.ts:165` — `Array.from(c.volumetric.data)`
  → `c.volumetric.data`.
- `src/webview/renderer.ts:984` — parameter typed `Float32Array`;
  body uses `data.data` directly instead of `new Float32Array(data.data)`.

CLI renderer (`scripts/render.ts:1699-1703`) intentionally NOT
changed — its volumetric path is JSON-stringified into an inline
HTML page (not postMessage), and `JSON.stringify(Float32Array)`
yields `{}`, so `Array.from` is required there. Different bottleneck,
out of scope.

## Memory impact

Post-patch, an N-point grid is held twice: once in the extension
host (parser's Float32Array), once in the webview (the same buffer
after structured clone). 8N bytes total instead of 24N. A 10 MB
cube goes from ~120 MB total RAM to ~40 MB.

(VSCode's documented "efficient ArrayBuffer transfer" still implies
one copy per process — the host's buffer is not moved/transferred,
only cloned faster. To get true 1× requires `transfer:[buffer]` in
the postMessage call which the VSCode API does not expose. 2×
across processes is the floor with current API.)

## What this does NOT solve

The reporter's "tens of GB" exciton wavefunction case is not
fixed by this patch alone. ASCII XSF / cube files larger than
~512 MiB will still fail at `vscode.TextDocument.getText()`
because of the V8 string-heap ceiling (`buffer.constants.MAX_STRING_LENGTH
= 536_870_888` bytes on Node 20). That's Tier 2 (v0.22 feat 22.2)
— streaming raw-byte parser path, planned but not implemented here.
