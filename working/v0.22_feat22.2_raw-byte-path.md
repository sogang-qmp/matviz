# v0.22 feat 22.2 — Raw-byte volumetric parser path

Done 2026-05-19. First feature of v0.22 (large-volumetric data support).
Implements Tier 2 from `plans/v0.22_large-volumetric.md`: bypass
`vscode.TextDocument.getText()` for cube / XSF / CHGCAR files larger
than 256 MiB so they no longer hit V8's `MAX_STRING_LENGTH = 536_870_888`
bytes ceiling (`RangeError: Invalid string length`).

## What changed

- **New `src/parsers/lineIterator.ts`** — `iterLines(buf: Uint8Array)`
  generator, `findBytes(haystack, needle)`, `offsetAfterLines(buf, n)`.
  Handles `\n`, `\r\n`, bare `\r` line endings. BOM stripped by
  `TextDecoder`. Each yielded line is materialized as a JS string, so
  the helper is only safe for formats where individual lines stay well
  under 512 MiB — true for ASCII scientific volumetric formats where
  lines hold at most a handful of floats.
- **`src/parsers/cubeParser.ts`** — extracted `parseCubeHeader()` to
  share between string-path and byte-path. Added `parseCubeFromBytes()`
  that decodes only the header (`6 + nAtoms` lines, a few KB max) as a
  string and iterates the grid blob byte-by-byte. No intermediate
  full-grid Float32Array allocation.
- **`src/parsers/xsfParser.ts`** — added `parseXsfFromBytes()` which
  splits the file at `BEGIN_BLOCK_DATAGRID_3D`, decodes the header
  slice and reuses `parseXsf` for atom/lattice parsing, and runs a new
  `parseDatagrid3DFromBytes()` state-machine for the grid blob.
- **`src/parsers/chgcarParser.ts`** — added `parseChgcarFromBytes()`.
  Reads a 256 KB header peek to locate the POSCAR/grid boundary
  (covers any plausible atom count), parses POSCAR via the existing
  `parsePoscar`, then iterates the charge grid by line.
- **`src/parsers/index.ts`** — exposes `parseStructureFileTrajFromBytes()`
  (byte-path entry point, dispatches by filename) and `hasBytePath()`
  (extension predicate). Symmetry post-pass (`withSymmetry`) applied on
  frame 0 same as the string path.
- **`src/editor/crystalEditorProvider.ts`**:
  - Added `RAW_BYTE_THRESHOLD = 256 MiB`.
  - Added `usedRawBytePath?: boolean` to `ParsedContent`.
  - Added `parseDocumentInitial()` async wrapper used at editor open:
    stats the file, picks byte path if `size ≥ threshold` and a
    byte-path parser exists for the extension, otherwise falls back to
    the existing TextDocument path.
  - `resolveCustomTextEditor` initial parse is now `await`-ed.
  - `onDidChangeTextDocument` debounced reparse loop now **no-ops**
    when `content.usedRawBytePath === true` — rereading a 1+ GB file
    on every keystroke is untenable, and VSCode's
    `editor.largeFileOptimizations` disables most editing affordances
    at that size anyway.

## Validation

**Bit-equal byte-path vs string-path on existing fixtures** (new
`scripts/test-byte-volumetric.ts`, run via `npx tsx`):

```
[h2o.cube]
  OK   species length / symbols
  OK   lattice agrees
  OK   positions agree
  OK   volumetric presence / dims / origin / lattice / data length
  OK   data bit-equal

[LiF-polaron-isolevel.xsf]
  OK   species length / symbols
  OK   lattice / positions
  OK   volumetric (dims, origin, lattice, data length)
  OK   data bit-equal (every Float32 matches)
```

**Threshold-gate exercise on a synthesized 297 MiB cube** (300³ grid,
27 M points; generated in /tmp, not committed):

| metric | byte path | string path (control) |
|---|---|---|
| parse time | 3,975 ms | 3,181 ms |
| RSS delta after parse | 108 MiB | (not measured) |
| data bit-equal to byte path | — | YES |

RSS delta of 108 MiB matches `Float32Array(27e6) = 108 MB` exactly,
i.e. the byte path adds ~zero overhead beyond the grid itself —
intermediate Uint8Array gets GC'd promptly.

Build (`npm run build`) and `npx tsc --noEmit` both clean.

## What this does NOT solve

- **Files where the Float32 grid itself would exceed
  `buffer.constants.MAX_LENGTH = 4 GiB`** — i.e., grids with
  > 2^30 ≈ 1.07 × 10⁹ points (≈ 1024³). The byte path will throw
  `RangeError: Array buffer allocation failed` at
  `new Float32Array(totalPoints)`. For the reporter's "tens of GB"
  case, if the ASCII source is, say, 30 GB at ~60 bytes/point that
  implies ~5×10⁸ points (≈ 800³) and ~2 GB of Float32 — fits. But a
  true ~10 GB Float32 grid (≈ 1350³) will hit this ceiling.
  **Mitigation requires Tier 3 (feat 22.3) load-time downsampling**,
  applied during ingestion before the full Float32Array is
  materialized — so 22.3 is now load-bearing for the original report,
  not "opt-in nice-to-have." Reporter's actual file size still needs
  to be requested to know which side of this line we're on.

- **Webview-side UI freeze on huge grids.** Once the host has parsed
  and the grid arrives in the webview, `renderer.loadVolumetric` runs
  a full O(N) max/min scan and triggers a marching-cubes pass —
  synchronous, on the main thread. For 100+ million points this is
  multi-second. "Opens successfully" in this feature's claim means
  "host parses + structured-clones the data into the webview without
  the OOM/RangeError that v0.20.0 had"; sub-second responsiveness is a
  separate concern (would require web worker offload or progressive
  marching cubes, both out of v0.22 scope).

- **CHGCAR validation.** No CHGCAR fixture in `test/fixtures/` so the
  byte path for CHGCAR is only validated by code review and shared
  helper coverage. Real CHGCAR users in v0.22 manual testing should
  exercise this.

## Follow-ups

- Feat 22.3 — load-time downsampling. Now more important than the
  plan originally suggested (see "What this does NOT solve").
- Webview-side N-pass scans (`loadVolumetric` max/min, isosurface
  build) — separate optimization, file in v0.22 follow-up backlog
  if it bites in practice.
- The CLI renderer (`scripts/render.ts`) still goes through
  `JSON.stringify(Array.from(Float32Array))` for inline-HTML data
  injection — has a similar string-size ceiling but is a different
  bottleneck. Not in v0.22 scope; flag if a large-grid CLI render
  hits it.
