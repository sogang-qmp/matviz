# v0.22 feat 22.3 — Load-time downsampling

Done 2026-05-19. Second feature of v0.22, immediately following feat 22.2.
Implements Tier 3 from `plans/v0.22_large-volumetric.md` with one
significant change of plan: downsampling is **not** opt-in any longer.
A safety default cap (4×10⁸ points) auto-applies when the user has not
explicitly set `matviz.volumetric.maxGridPoints`. This is necessary
because the byte-path parser's `new Float32Array(N)` allocation itself
hits the 4 GiB ArrayBuffer ceiling at N ≈ 10⁹ — the failure mode 22.2
left open. With 22.3 the byte path now degrades gracefully (lower
resolution) instead of throwing `RangeError: Array buffer allocation
failed`.

## What changed

- **`src/parsers/types.ts`**:
  - `VolumetricData` gains optional `stride?: number` and
    `originalDims?: [number, number, number]` fields. Present when
    load-time decimation was applied; absent on stride-1 loads.
  - New `VolumetricLoadOptions` interface carrying `maxGridPoints`.
  - Exported `VOLUMETRIC_SAFETY_MAX_GRID_POINTS = 4e8` constant. ~730³,
    ~1.6 GB Float32 — half the 4 GiB ArrayBuffer ceiling. Tuned to
    leave headroom for the source Uint8Array + V8 internals + the
    webview's structured-clone copy.
  - Exported `chooseStride(nx, ny, nz, cap)` helper. Smallest integer
    `s ≥ 1` such that `ceil(nx/s) * ceil(ny/s) * ceil(nz/s) ≤ cap`.
    Single uniform stride across all three axes — **isotropic**
    decimation, not per-axis.
- **All three `*FromBytes` parsers**:
  - Accept optional `VolumetricLoadOptions`.
  - Compute stride before allocating the result Float32Array, so the
    full-resolution grid is never materialized when the source would
    exceed the cap.
  - Apply the stride during ingestion: only tokens at indices where
    all three of `(ix, iy, iz)` are multiples of `stride` are written
    to the output array. Source ordering preserved (Fortran for XSF /
    CHGCAR, C order with iz fastest for Cube).
  - Populate `stride` and `originalDims` on the result when stride > 1.
- **`src/parsers/index.ts`**: `parseStructureFileTrajFromBytes`
  forwards `options` to the per-format parser.
- **`src/editor/crystalEditorProvider.ts`**: reads the new VSCode
  setting `matviz.volumetric.maxGridPoints` on every parse (so
  toggling it in settings.json takes effect at the next reparse) and
  passes it as `options.maxGridPoints` to both the string-path
  (`parseDocument` → `parseStructureFileTraj`) and byte-path
  (`parseDocumentInitial` → `parseStructureFileTrajFromBytes`)
  entries. Null means "no user cap — leave native resolution"; the
  byte-path raw loader still falls back to its internal safety cap
  (`VOLUMETRIC_SAFETY_MAX_GRID_POINTS`) to stay below the 4 GiB
  ArrayBuffer ceiling.

  **Semantics: user-set cap applies universally; safety default
  applies only when the byte path is engaged.** The earlier
  byte-path-only behavior was a design mistake — it meant users with
  routine sub-256-MiB cubes who set a small cap saw no effect, and
  the info-pill stride indicator was unreachable in normal workflows.
- **Post-parse decimation** is performed by a new
  `decimateVolumetric(v, options)` helper in `types.ts`. The byte
  path applies stride **during ingestion** (the only way to handle
  grids that would exceed the 4 GiB allocation ceiling); the string
  path applies stride **post-parse** since at sub-256-MiB sizes the
  full grid already fits. Both code paths produce bit-equal output
  for the same cap on the same file (verified in
  `scripts/test-byte-volumetric.ts`).
- **`package.json`**: registers
  `matviz.volumetric.maxGridPoints: number | null` (default null) under
  `contributes.configuration.properties`.

## Why isotropic stride (and not per-axis)

The user raised the concern: "한 방향으로만 줄이는 것은 의미가 없을 것
같아." Confirmed — `chooseStride` returns a single integer applied to
all three axes simultaneously, and the ingestion gate is

```ts
if (ix % stride === 0 && iy % stride === 0 && iz % stride === 0) emit;
```

so the output volume shrinks by `stride³`, not by `stride`. Reasons:

1. Physical volumetric fields (charge density, exciton wavefunction,
   molecular orbitals) vary on comparable spatial scales in each
   Cartesian direction — anisotropic decimation distorts isosurface
   topology.
2. `Math.ceil` in `chooseStride` ensures short axes never go below 1,
   so 1000×100×100 with stride 4 becomes 250×25×25 (1.56×10⁵ points)
   — the longer axis still keeps more samples in absolute terms.
3. Per-axis stride is only meaningful when the source is extremely
   anisotropic; if needed, it can be added later behind an explicit
   setting (e.g., `maxAnisotropy`) without breaking the current
   default.

## Validation

Re-ran `npx tsx scripts/test-byte-volumetric.ts` after extending it
with a stride-verification block.

- **Existing fixtures (h2o.cube, LiF-polaron XSF):** stride=1 selected
  (source ≪ cap), all bit-equality checks unchanged from 22.2. No
  regression.
- **Forced-stride test on LiF polaron XSF, `cap = 1e4`:**
  - source dims `64×64×64` (262 144 points)
  - chosen stride: **4** (because `16³ = 4096 ≤ cap`, `21³ = 9261 ≤ cap`
    but `21³` would only pass if `chooseStride` accepted non-integers;
    actually `ceil(64/3) = 22, 22³ = 10648 > cap`, so it picks 4)
  - output dims `16×16×16` (4096 points)
  - `originalDims` correctly reports `64×64×64`
  - **every output value matches `fullGrid[oi×stride, oj×stride,
    ok×stride]`** — bit-equal to the corresponding full-grid stride
    samples in all three dimensions.

Build (`npm run build`) and `npx tsc --noEmit` both clean.

## What this means for the original bug report

Combining 22.2 + 22.3:

- ASCII XSF / cube / CHGCAR files of any size that can be read as a
  `Uint8Array` (≤ 4 GiB on x64 Node) now load successfully.
- For grids that would have allocated > 1.6 GB of Float32 (~730³),
  ingestion automatically applies a stride to land under the cap.
- The user can tune the cap downward via
  `matviz.volumetric.maxGridPoints` for faster isosurface rendering
  on routine charge densities.

The reporter's "tens-of-GB exciton wavefunction" case is now covered
end-to-end on the host side, assuming the file is ≤ 4 GiB on disk
(typical for a 30-GB-ASCII = 5×10⁸-points scale). Files above 4 GiB
on disk (the `Uint8Array` itself can't hold them) remain unsupported
— that's a streaming-read problem distinct from the grid-allocation
problem 22.3 solved.

## Follow-ups

- **Info pill UI** — `VolumetricData.stride` / `originalDims` are
  populated but not yet surfaced. Add a secondary line on the
  bottom-left info pill, e.g. "isosurface: 1024³ → 512³ (stride 2)",
  so the user knows when they are seeing decimated data. Webview-side
  message + DOM change. Not in 22.3 scope.
- **CLI renderer parity** — `scripts/render.ts` does not consult the
  setting and does not have a byte path; the CLI cannot render
  oversized volumetric data. Out of v0.22 scope; flag if encountered.
- **Webview-side N-pass scans** — `renderer.loadVolumetric` still
  runs O(N) max/min scan and marching cubes on the main thread.
  Lower-priority now that 22.3 caps N at 4×10⁸, but for grids near
  that cap it is still a multi-second sync operation. Worker offload
  is the cleanest fix.
