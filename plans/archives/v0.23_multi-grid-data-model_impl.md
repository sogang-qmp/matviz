## Data-flow map (as of v0.22.1)

Single-grid assumption is baked into a 6-hop chain:

1. **Parsers** return one grid:
   - `chgcarParser.ts:8 parseChgcar` / `:145 parseChgcarFromBytes` → `{ structure, volumetric: VolumetricData }`
   - `xsfParser.ts:51 parseXsf` → `CrystalStructure & { volumetric? }`; `:299 parseDatagrid3D` reads the **first** `BEGIN_DATAGRID_3D` only; `:478 parseXsfFromBytes` / `:493 parseDatagrid3DFromBytes` (byte path)
   - `cubeParser.ts:67 parseCube` / `:100 parseCubeFromBytes`
2. **index.ts** — `ParseResult {structure, volumetric?}` (`:14`), `ParseTrajectoryResult {trajectory, volumetric?}` (`:19`); every branch returns a single `volumetric`.
3. **crystalEditorProvider.ts** — stores `volumetric?` (`:45`); posts `loadVolumetric` (`:212-222`) with the single grid inline.
4. **message.ts:9** — `loadVolumetric` carries one grid.
5. **main.ts:1624** — `case 'loadVolumetric': renderer.loadVolumetric(msg.data)`.
6. **renderer.ts** — `volumetricData: VolumetricData | null` (`:976`); `loadVolumetric` (`:979`); reads at `:882`, `:1008` (`getMaxAbs`), `:1019 buildIsosurface`, `:2008` (rebuild). `embed/index.ts:195` also calls `renderer.loadVolumetric`.

`VolumetricData` (`types.ts:37`) = `{origin, lattice, dims, data, stride?, originalDims?}`.

## Feature 23.1 — Named-grid data model (pure refactor, byte-identical) ✅ DONE (Gate v0.23-A passed 2026-07-22)

> See `working/v0.23_feat1_named-grid-data-model.md`. CLI pixel-diff on
> h2o.cube / LiF / band15 all sha256-identical to v0.22.1 baseline.
> Renderer `volumetricData` is now a getter over `volumetricGrids[activeGridIndex]`.

**Goal**: make the entire chain array-capable while every parser still
emits exactly one grid, so rendering is unchanged. This is the Gate
v0.23-A deliverable.

### 23.1.a — `types.ts`
Add two optional fields to `VolumetricData` (additive, non-breaking):
```ts
name?: string;                 // grid label; UI display + --grid select
kind?: 'scalar' | 'signed';    // default undefined ≡ 'scalar'
```
Keep `VolumetricData` as *the per-grid type*. A "grid set" is just
`VolumetricData[]`. No parallel `VolumetricGrid` interface (avoids churn).

### 23.1.b — `index.ts`
- Extend `ParseResult` / `ParseTrajectoryResult` with
  `volumetrics?: VolumetricData[]`. Keep `volumetric?` as a back-compat
  alias equal to `volumetrics?.[0]`.
- Add a helper `withGridList(r)` that, when `r.volumetric` is set and
  `r.volumetrics` is not, sets `r.volumetrics = [r.volumetric]` and gives
  the grid a default `name` if absent (`'density'` for cube/xsf,
  `'charge'` for chgcar-family — pass the format in). Apply in
  `parseStructureFile`, `parseStructureFileTraj`,
  `parseStructureFileTrajFromBytes`.
- `decimateVolumetric` stays single-grid; map it over the array when a
  cap is set.

### 23.1.c — `message.ts`
Add a plural message; keep the singular for the embed/back-compat path:
```ts
| { type: 'loadVolumetrics'; data: Array<{ /* same inline shape */ name?: string; kind?: 'scalar'|'signed' } & VolumetricInline> }
```
(where `VolumetricInline` = the existing `loadVolumetric.data` shape).

### 23.1.d — `crystalEditorProvider.ts`
- Store `volumetrics?: VolumetricData[]` alongside/replacing `volumetric`.
- Replace the `loadVolumetric` post (`:212-222`) with a `loadVolumetrics`
  post carrying the array (each grid's `origin/lattice/dims/data/stride/
  originalDims/name/kind`). Preserve the v0.20.1 zero-copy `Float32Array`
  transfer per grid.

### 23.1.e — `main.ts`
Add `case 'loadVolumetrics': renderer.loadVolumetrics(msg.data); break;`
Keep the `loadVolumetric` case (embed still uses the singular renderer
method; harmless).

### 23.1.f — `renderer.ts` (the getter trick)
- Replace the field (`:976`):
  ```ts
  private volumetricGrids: VolumetricData[] = [];
  private activeGridIndex = 0;
  private get volumetricData(): VolumetricData | null {
    return this.volumetricGrids[this.activeGridIndex] ?? null;
  }
  ```
  Every existing `this.volumetricData` **read** (`:882,:1008,:1019,:2008`)
  is now getter-backed — unchanged behavior.
- `loadVolumetric(single)` → `this.loadVolumetrics([single])` (keep for embed).
- New `loadVolumetrics(arr)`: normalize each grid (the existing
  `:980-990` normalization/clone), store into `volumetricGrids`, set
  `activeGridIndex = 0`, then `buildIsosurface()`.
- Add `setActiveGrid(i)` (used by 23.4): clamp `i`, rebuild iso. **Not
  wired to UI in 23.1** — internal only.

### 23.1.g — `embed/index.ts`
No change required (keeps calling `renderer.loadVolumetric(volumetric)`
= `volumetrics[0]`). Confirm `result.volumetric` still populated via the
back-compat alias.

## Feature 23.2 — XSF multi-DATAGRID ✅ DONE (2026-07-22)

> `parseDatagrid3D` → `parseDatagrids3D` (string) + `parseDatagrids3DFromBytes`
> (byte); each grid named from its `BEGIN_DATAGRID_3D_<label>` suffix.
> `parseXsf`/`parseXsfTraj`/`parseXsfFromBytes` return `volumetrics[]`.
> Verified: `xsf-two-datagrid.xsf` → 2 grids (grid_A/grid_B), correct data.
> **Deviation**: multi-block cell-vector mismatch is *tolerated* (each grid
> renders independently) rather than erroring as the manual suggests —
> keeping all grids is the useful multi-grid behavior. See working log.

### (original plan)

- Generalize `parseDatagrid3D` (`xsfParser.ts:299`) to loop over **all**
  `BEGIN_DATAGRID_3D` inside all `BEGIN_BLOCK_DATAGRID_3D`, returning
  `VolumetricData[]`, each named from the grid label line (the token
  after `BEGIN_DATAGRID_3D`, or `datagrid_${n}`). Apply
  `trimRedundantPeriodicPlanes` + `snapGridLatticeToCell` per grid.
- Mirror in `parseDatagrid3DFromBytes` (byte path); multi-block byte-path
  only trims when `stride==1` (existing rule).
- Reject mismatched dims/lattice across blocks with a clear `Error`.
- `parseXsf` returns `volumetrics` (first stays `volumetric` alias).

## Feature 23.3 — CHGCAR spin/SOC ✅ DONE (2026-07-22)

> `parseChgcar` + `parseChgcarFromBytes` now read all grid blocks (skipping
> PAW `augmentation` via `isDimsLine` delimiter). `buildChgcarGrids()`
> classifies: 1→[charge]; 2→[charge, magnetization, spin_up, spin_down];
> 4→[charge, magnetization_x/y/z]. Verified: collinear + SOC fixtures →
> 4 grids each, correct names/kinds, `up±dn` identity, byte path bit-equal
> to string path.
> **Deviation from plan D3**: spin_up/down derived **eagerly** (4 resident
> grids) not lazily — self-contained, matches manual's 4-entry Model Tree,
> memory bounded by v0.22 `maxGridPoints` decimation. See working log.

### (original plan)

- In `parseChgcar` / `parseChgcarFromBytes`, after the first grid, **skip
  augmentation** sections and read subsequent grids delimited by a repeat
  of the exact `nx ny nz` dims line. Collect raw grids `g[0..k-1]`.
- Classify by count: 1 → `[charge]`; 2 → `[charge, magnetization]` then
  derive `spin_up=(c+m)/2`, `spin_down=(c-m)/2` (lazy — see plan D3);
  4 → `[charge, magnetization_x, magnetization_y, magnetization_z]`.
- Volume-normalize each grid (existing scale). Tag mag/σ grids
  `kind:'signed'`, charge `kind:'scalar'`.
- Guard: a claimed grid with < `nx·ny·nz` floats → fall back to
  single-grid (never crash).
- **New fixtures**: `test/fixtures/chgcar-collinear-spin`,
  `test/fixtures/chgcar-soc-noncollinear` (small, hand-built).
