# v0.22 — Large volumetric data support

## Goal

Make MatViz survive opening volumetric files (Gaussian Cube, XSF
`BEGIN_DATAGRID_3D`, VASP CHGCAR) far larger than today's practical
ceiling — specifically, ASCII volumetric files in the hundreds-of-MB
to multi-GB range, motivated by exciton wavefunctions exported from
BerkeleyGW `plotxct` and large supercell charge densities.

Today's ceiling, established by code + Node.js runtime inspection:

- `Array.from(Float32Array)` in `crystalEditorProvider.ts:165`
  forces a 4N→8N boxed `number[]` copy, then structured-clone gives a
  second 8N copy in the webview process, then `new Float32Array(...)`
  in `renderer.ts:983` gives a third 4N copy. ≈24N bytes total RAM
  for an N-point grid even after parsing.
- `vscode.TextDocument.getText()` returns a single JS string;
  `buffer.constants.MAX_STRING_LENGTH = 536_870_888` bytes
  (~512 MiB) on Node 20 x64. Any ASCII volumetric file above that
  size throws `RangeError: Invalid string length` and the editor
  cannot even start parsing.

## Why now

A user reported (2026-05-19) that MatViz crashes on
"tens-of-GB" exciton wavefunctions. The investigation surfaced that
the failure is two distinct problems stacked: a memory-amplification
bug that affects *every* volumetric load (even small ones),
and a V8 string-heap wall that kicks in around 512 MiB. The first is
a 3-line fix worth shipping regardless. The second is a structural
limitation that determines whether GW/BSE workflows are viable in
MatViz at all.

Doing this before v0.21 (Web SPA) means the SPA inherits a working
large-file path; doing it after would require porting fixes twice
(host parser + browser File-API parser).

## Roadmap impact

Inserts ahead of v0.21 (Web SPA on github.io). v0.21's exit criteria
do not depend on volumetric handling, so reordering is clean. If the
user prefers, this work can also ship as **v0.20.1** (Tier 1 only)
+ deferred v0.22 (Tier 2/3) — see "Phasing" below.

## Scope (3 features, tiered)

| # | Feature | Success criterion |
|---|---------|-------------------|
| 22.1 | **Tier 1 — Kill the 3× volumetric copy** | Loading a 200 MB cube fixture uses ≤2× the file's grid-bytes in steady-state RAM (measured via `process.memoryUsage().heapUsed` delta + webview devtools). `Array.from` removed from `crystalEditorProvider.ts:165`; message type `LoadVolumetricMsg.data.data` is `Float32Array`; `renderer.ts:983` stores the typed array directly without re-copying. No regression on small (<10 MB) fixtures. |
| 22.2 | **Tier 2 — Bypass TextDocument for large volumetric files** | A 1.5 GB ASCII XSF with `BEGIN_DATAGRID_3D` opens successfully where today it fails with `RangeError: Invalid string length`. Triggered automatically when `file.size > MATVIZ_VOLUMETRIC_RAW_BYTES_THRESHOLD` (default 256 MiB) **and** extension matches `.cube`/`.xsf`/`CHGCAR`. Falls back to current TextDocument path otherwise. Editor "split text pane" UX for these files: text editor shows nothing or a stub message ("file too large for text view") — visualization still works. |
| 22.3 | **Tier 3 (opt-in) — Load-time downsampling** | New setting `matviz.volumetric.maxGridPoints` (default `null` = no cap; suggested `2e8`). When set and exceeded by the loaded grid, parser performs strided sampling on the fly during ingestion, so peak RAM stays bounded regardless of source file size. Status pill shows "downsampled M³ → m³" indicator. |

## Out of scope

- Binary volumetric formats (HDF5, NetCDF, BerkeleyGW `eigenvectors.h5`).
  No bindings today; would add an order of magnitude of dependency
  surface. Tracked as future work; not part of v0.22.
- True out-of-core rendering (brick-based 3D texture, GPU upload of
  subvolumes). WebGL `MAX_3D_TEXTURE_SIZE` is not the bottleneck for
  the use cases we care about; Marching Cubes runs on CPU here.
- Multi-grid XSF files (more than one `BEGIN_DATAGRID_3D` block per
  file). Today only the first grid is read; that stays true.
- Changing the editor provider model
  (`CustomTextEditorProvider` → `CustomReadonlyEditorProvider`). The
  Tier 2 design works *within* the current provider by stat-gating
  the read path; provider migration is deferred until v0.23+ if
  ever needed.

## Risks / decisions

- **D1: Provider model drift.** `CLAUDE.md` documents the provider as
  `CustomReadonlyEditorProvider<CrystalDocument>` but the code is
  `CustomTextEditorProvider` (signature
  `resolveCustomTextEditor(document: vscode.TextDocument, ...)`).
  This plan assumes the code is authoritative. **Action: update
  CLAUDE.md to match reality before Tier 2 begins** — but as a
  housekeeping edit, not as a feature.

- **D2: Where does the size threshold live?** Tier 2 needs the file
  size *before* parsing. `document.getText()` doesn't expose it
  cheaply; we get size from `vscode.workspace.fs.stat(document.uri)`
  in `parseDocument()`. One extra stat per load is negligible.

- **D3: When the raw-byte path is active, the in-editor text buffer
  loses sync.** Users editing a 1 GB CHGCAR in the text pane is not
  a real workflow — `editor.largeFileOptimizations` already disables
  most editing affordances at that size — but we should explicitly
  disable the debounced reparse-on-change loop for raw-byte loads
  to avoid silently dropping edits.

- **D4: Endianness / locale.** ASCII float parsing is locale-free
  (`parseFloat` ignores `LANG`), so no concern there. But the
  byte-buffer line tokenizer must handle `\r\n`, `\n`, and `\r` line
  endings (XSF files from Windows / old Macs exist in the wild).

- **D5: Downsampling default.** Tier 3 default is `null` (off) — we
  do not want to silently change what users see. Opt-in only.

## Phasing — decided 2026-05-19 (option A)

Tier 1 already shipped as **v0.20.1** (patch release, 2026-05-19) —
see `working/v0.20.1_feat1_volumetric-zero-copy.md`. v0.22 covers
**Tier 2 + Tier 3 only**. Feature 22.1 in this document is preserved
for historical context; mark it as completed when v0.22 kicks off.
