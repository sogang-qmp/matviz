# v0.21 — Embeddable page widget (pivot from standalone SPA)

**Kickoff date**: 2026-07-22
**Status**: awaiting Gate-21.A approval

## Pivot summary

The Plan.md v0.21 entry described a **standalone SPA on github.io** (drag-drop,
`?file=URL`, Materials Project fetch, permalink share, sample gallery). Per the
2026-07-22 direction change, v0.21 instead ships an **embeddable widget** that
drops into an existing web page — modeled on the `sogang-qmp/recipes`
house pattern (`structure-viewer.html`, currently 3Dmol-based):

> engine script included **once** per page + one `<div>` per figure + an inline
> data block + a single `MatViz.mount("id", {...})` call. Add a structure by
> swapping the inline data string.

Three user requirements drive the re-scope:

1. **Page-inside embed**, not a standalone site — HTML *fragment*, no
   `<html>/<head>/<body>`, inserted into the portal layout.
2. **UI collapsed by default** — page-inside means chrome must recede; the
   canvas is the figure, controls open on demand.
3. **Host-theme reactivity** — matviz palette follows the host page's
   light/dark, live.

## Deployment target (verified 2026-07-22)

Primary host: **`sogang-qmp/112-Gd2C-H/site`** — an offline project-site shell
(the `sogang-qmp/000-project-template` v2 shell) that consumes
`sogang-qmp/recipes` components. Real embeddings live in e.g.
`site/electronic-structure/112-p31m-cell/index.html` (3Dmol today).

## Hard constraints inherited from the host site

- **`file://` offline-first** — pages open by double-click, **no web server, no
  build, no fetch of any kind.** Stricter than the recipes CSP. All structure
  data is inline; all libs are vendored in `site/assets/lib/`.
- **No `'wasm-unsafe-eval'`** (recipes sandbox CSP) → spglib WASM can't run.
- **Heavy libs self-hosted, depth-resolved** — a depth-2 page loads
  `../../assets/lib/3Dmol-min.js`; `matviz-embed.js` sits alongside it as
  `site/assets/lib/matviz-embed.js`, referenced with the page's `../` depth.
- **Inline data** via `<script type="text/plain" id="{prefix}-data">…</script>`
  or a data-JS global (`window.FOO = {…}` + `<script src="data/foo.js">`).
- **Theme signal is known and exact** (from `site/assets/site.js`):
  `document.documentElement.dataset.theme` = `"light"` \| `"dark"`, toggled by
  the shell's top-right ◐ button, persisted in `localStorage['site-theme']`,
  defaulting to `prefers-color-scheme`. The shell drives colors through CSS
  vars on `[data-theme="dark"]`: `--bg` (`#fff`→`#191b1f`), `--fg`, `--muted`,
  `--border`, `--rule`.
- **Today's 3Dmol embeds hardcode `backgroundColor:"white"`** — they do NOT
  follow the ◐ toggle. matviz's host-theme reactivity (21.5) is the concrete
  value-add over the existing 3Dmol recipe.
- **UI aux text uses `opacity`, not fixed colors** (house rule); **container
  `id` namespaced by a component prefix** (collision-safe).

## Kickoff decisions (locked 2026-07-22 via user Q&A)

- **Theme detection = `auto`**: observe `document.documentElement`'s
  **`data-theme`** attribute (the host shell's exact signal) via
  `MutationObserver`, with `prefers-color-scheme` as the fallback when the
  attribute is absent. Reuses the existing observer in `main.ts:1136` (today it
  watches `data-vscode-theme-kind`; embed retargets it to `data-theme` on the
  root). `themeAttribute`/`themeClass`/`themeTarget` overridable for other hosts;
  `theme:"light"|"dark"` also accepted (fixed). Optionally read the host CSS vars
  (`--bg`/`--fg`/`--border`) so the widget blends into the page card exactly.
- **Symmetry omitted in the embed**: no spglib WASM (CSP forbids it). Info pill
  shows the CIF-declared space group when present, else `P1`. Non-fatal — this
  is already the legacy fallback path (`withSymmetry` degrades gracefully).
- **Separate recipe**: keep the lightweight 3Dmol `structure-viewer.html`; add a
  new `structure-viewer-matviz.html` for the advanced matviz viewer
  (isosurface, polyhedra, measurement, trajectory) that 3Dmol can't do.

## Out of scope (dropped from the original SPA plan)

Removed because the embed target + `connect-src 'none'` make them impossible or
irrelevant:

- Standalone `twinace98.github.io/matviz` page and GitHub Actions Pages deploy.
- Drag-drop file loading, `<input type=file>`, `?file=<URL>` param.
- Materials Project / Optimade HTTPS fetch (**violates `connect-src 'none'`**).
- Permalink/share-URL hash encoding (portal owns the URL; fragment can't).
- Separate sample-gallery page (samples become inline data blocks in the recipe).

CLI renderer (`scripts/render.ts`) parity is unaffected — separate code path.

## Decision gates

- **Gate-21.A — Kickoff approval** (this plan + impl spec). ⟵ *current gate.*
- **Gate-21.B — Build tool**: esbuild (third entry, matches the existing
  dual-bundle) vs Vite. Default: **esbuild** — one tool, no dev-server need for a
  single static asset. Decide at 21.1.
- **Gate-21.C — Collapsed-UI visual review**: mount in a real recipe-style host
  page, confirm the collapsed figure reads cleanly and expands correctly, in
  both host themes. (Mirrors v0.18 Gate-B.)
- **Gate-21.D — Pre-release CSP + theme audit**: static bundle loads and runs
  under `script-src 'self' 'unsafe-inline'; connect-src 'none'` with **zero**
  network requests and **no** wasm; host light↔dark switch verified live.

## Exit criterion

`structure-viewer-matviz.html` renders CIF / POSCAR / XSF (incl. vectors and an
isosurface) from **inline** data inside a recipe host page; chrome is collapsed
by default and expands on demand; matviz theme follows the host light/dark
switch reactively; the whole thing runs under the portal sandbox CSP with no
external network and no wasm. `matviz-embed.js` self-hosted at `static/lib/`.
VSCode extension bundle unchanged.
